# 本地适航问答上下文预算与整理恢复修复计划

## 目标

用户在已有项目对话中上传试验大纲 DOCX 并提出明确问题后，应用能够读取相关模板段落、检索项目条款、生成带可核对引用的回答。上下文准备根据实际输入预算和任务依赖选择内容。历史整理失败时，根据本轮任务依赖决定继续执行或说明具体缺失项。

## 执行方式

后续实施使用 superpowers:executing-plans 技能逐项执行。各任务先增加对应回归用例，验证失败后实施最小修改，再运行相关回归。当前文档包含设计和实施步骤。各步骤的完成状态在实施时填写。

## 技术基础

Python Core、SQLite、现有 ContextEngineService、上下文快照、RagGrounding、独立文档解析进程、应用托管 llama.cpp、React/Tauri 桌面界面。

## 已核实的问题

- 当前模型实际配置为 Qwen3 1.7B Instruct、CPU、3 线程、8,192 token 窗口。
- resolve_budget 将日常输入目标计算为窗口的 55% 再减去回答预留。8,192 窗口、2,048 回答预留时，目标约 2,457，输入硬限约 4,915。
- 当前代码复算的基础输入约 3,442 token，包括系统指令 1,098、当前问题和附件说明 700、证据格式指令 147、两条证据 595、历史消息 902。该数值采用应用估算器，额外技能和传输封装应在最终组装中统一计入。
- pack_context 在任何历史轮次因预算被排除时抛出 context_compaction_required。
- 附件原文已成功保存和解析，本轮采用有限片段。已检索到第 8.1 条，物理第 46 页。
- 本机真实整理运行约 895 秒，经过一次纠正仍报 context_compaction_unreliable，尚未进入最终回答生成。
- 当前整理仅使用 json_object，并要求模型生成九类摘要、来源编号和信任等级。日志缺少明确的校验失败分类。

## 设计原则

1. 使用应用当前实际加载的上下文窗口和现有回答预算计算输入容量。
2. 日常目标用于安排后台维护，输入硬限用于判定本轮是否能够执行。
3. 当前请求、显式引用、适用项目事实、当前任务要求和有效证据具有明确优先级。
4. 历史选择遵循完整轮次和工具调用配对，保留任务依赖。省略范围写入上下文快照。
5. 原始聊天、附件和证据身份保存于现有存储中，模型摘要包含可追溯来源。
6. 资料撤回、项目授权、文件版本、引用摘录与来源哈希检查参与执行和发布。
7. 前台回答与后台整理分别记录状态。任务依赖无法恢复时，显示具体缺失内容。
8. 本地推理和线上调用分别使用已有超时与调用策略。

## 一 统一预算

### 预算公式

- W 为当前加载窗口，受模型声明上限约束。
- R 复用 resolve_output_budget 得到的回答预留。
- 输入硬限 H = floor(W × 0.85) − R。
- 日常维护目标 T = floor(H × 0.80)。
- W = 8,192、R = 2,048 时，H = 4,915、T = 3,932。

系统消息、当前输入、附件片段、证据、历史、工具定义及响应 Schema 进入同一预算账本。最终传输封装通过既有适配器和预算检查复核。回答预留仅扣减一次。

T 作为后台整理参考。到达 T 后，符合依赖要求且最终序列化输入在 H 内的请求进入生成。

若必需输入超过 H，按顺序缩减可选历史、重复内容和可重新读取的附件外围段落。关键条款的适用条件、否定、例外和脚注通过父条款展开或拆分子任务处理。无法形成完整的必需输入时返回明确缺口或容量状态。

## 二 历史选择与任务依赖

### 选择规则

1. 装入当前用户请求和本轮明确选择的附件范围。
2. 保护用户显式引用的消息、当前任务起始要求及已确认项目事实。
3. 装入本轮适用证据，按问题相关性和父条款完整性选择。
4. 在剩余预算内选择最近完整对话轮次及与当前问题相关的历史。
5. 对模型生成的旧回答按历史来源处理，适航事实使用当前授权资料重新检索。
6. 对“沿用上面的类别”“按刚才的设备配置”等依赖型问题找回对应原始确认记录。
7. 依赖定位存在歧义时，返回缺失引用或需要确认的具体信息。

本期复用执行意图和已有附件引用元数据判断任务连续性。分类优先使用明确任务信息和规则。无法可靠识别新任务边界时，保护当前任务原始要求及用户约束。

### 前台判定

- 必需输入齐全且在 H 内，进入生成。
- 可选历史超出预算，记录省略范围并继续本轮。
- 任务依赖历史尚未恢复，尝试有界找回或整理，失败后显示缺失项。
- 当前请求或完整必要证据本身超限，提示缩小填写范围或拆分任务。

## 三 附件与 RAG 上下文

- 复用已保存的解析产物，读取目标标题、段落和表格位置。
- 对本次模板问题优先定位“试验程序 → 振动试验 → 试验目的”，携带父标题和定位信息。
- 为附件正文构建可检索的正文视图，定位元数据单独保存。选段评分使用正文和标题。
- 显式选定的附件范围优先于自动选段。
- 对关键词存在歧义的选段展示定位和范围，允许原文展开。
- RAG 预算依据输入硬限、必需任务内容及候选条款长度动态分配，默认上限 6,000 token。
- 证据进入上下文前检查父条款关系，回答引用仅接受实际装入的证据。
- 摘录复用已有 quote_id，来源、版本、页码和哈希由应用提供。
- 单个字段回答需要额外条款时，追加检索后重新执行预算与资料变更检查。

## 四 历史整理可靠性

### 触发与执行

- 回答完成后，根据历史选择结果和现有 minimum_compaction_reclaim 判断是否安排后台整理。
- 同一会话同时执行一个整理任务，避免与前台生成争用模型槽位。
- 当前请求必需历史未恢复时可执行前台整理，界面显示具体原因。
- 本地继续按检查点覆盖位置单调前进，取消、超时和无进展状态形成明确终态。
- 后台整理失败时保存诊断。后续请求根据任务依赖和现有可用信息判定可执行性。

### 结构化生成

整理输出采用受限条目数组，每条包含类别、简短内容和短来源编号。类别采用现有九类的枚举，来源编号映射到本次授权源。

程序将生成结果转换为现有内部检查点结构，填充空分类并根据来源推导信任等级。已有完整检查点验证器验证转换结果。历史九类检查点按既有结构读取。

llama.cpp 路线启用经过当前固定版本实测的 JSON Schema。整理提示同步给出结构示例。协议明确报告不支持时，执行已记录的 JSON 模式或文本格式回退，并标明实际采用的模式。

每次最多一次内容纠正，纠正提示包含静态错误分类、字段路径和允许来源编号。诊断记录解析阶段、错误分类、耗时、输入输出计数、模型与约束模式。

## 五 界面反馈

- 展示上下文窗口、预计输入、回答预留、输入硬限和历史省略数量。
- 对附件显示实际采用的标题路径、段落或物理页范围。
- 前台阶段使用“读取附件”“检索条款”“准备输入”“生成回答”“校验引用”。
- 后台整理显示独立状态和本段耗时，使用模型名称。
- 需要历史依赖时显示缺失项和处理入口。
- 整理失败显示实际错误。原始消息与附件继续通过现有恢复入口访问。
- 前台与后台的取消操作分别作用于其所属任务。

## 八 验收场景

### 主验收

使用现有的试验大纲 DOCX，在原项目长对话中发送“填写振动试验的试验目的，并列出验证能力、条款号、原文摘录、物理页码及资料缺口”。

完成条件如下。

1. 读取对应模板章节并显示采用范围。
2. 按本轮必要内容和预算直接进入问答准备。
3. 命中 DO-160F 第 8.1 条、物理第 46 页。
4. 回答说明性能标准与耐久性要求，并采用有效的原文摘录。
5. 如分析结构完整性，引用其具体支持条款。
6. 明确模板引用 DO-160G 与当前资料 DO-160F 的版本差异。
7. 设备类别、安装位置等资料缺口按原始输入情况列出。
8. 历史编辑、版本撤回和跨项目访问检查通过。
9. 同一条消息恢复时保持幂等，已完成阶段能恢复，取消能回收本轮任务资源。

### 对照验收

- 同样问题分别在新对话与原长对话运行，核对关键结论与证据一致性。
- 以“沿用上次确认的类别”测试必要历史找回。
- 多附件、长表格和跨页例外条款测试正确选段与完整引用。
- 强制后台摘要返回无效 JSON，核对独立问答继续执行及依赖型请求的明确提示。
- 记录当前 CPU 配置下的准备时间、检索时间、首 token、生成时间和峰值资源。CUDA 性能单独记录实际设备、卸载层数及结果。

## 九 实施边界与完成判定

本计划覆盖现有问答流程的上下文可靠性。模板批量字段映射和完整 DOCX 自动回填属于后续工作流扩展，当前验收先完成单个模板问题的带证据回答。

自动化通过和本机主验收共同构成完成条件。性能结果记录实测值。若发生失败，验收报告注明阶段、具体错误和已验证范围。
